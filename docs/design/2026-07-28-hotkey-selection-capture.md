# ホットキーによる選択テキスト取得の信頼性改善

日付: 2026-07-28
対象: `src-tauri/src/lib.rs` の `hotkey_handler`

## 背景

ホットキーを Alt+T に変更した環境、およびリモートデスクトップ (RDP) 経由の環境で、
選択中のテキストが取得されないことがある。原因は `hotkey_handler` の自動 Ctrl+C 処理に
3 つある。

1. **修飾キーの解放待ちが 130ms 固定**
   合成 Release を撃った 30ms 後に Ctrl+C を送るが、人間が Alt+T を離すのはたいてい
   それより遅い。押されたままの Alt がキーリピートで再び down になり、実際に送られるのが
   `Ctrl+Alt+C` になる。多くのアプリでこれはコピーにならない。
   デフォルトの Ctrl+Shift+Z では Ctrl が残っても `Ctrl+C` は成立するため顕在化しなかった。

2. **クリップボード反映待ちが 150ms 固定**
   RDP はクリップボードをリダイレクトするため、コピーがローカルに反映されるまで
   数百 ms かかることがある。間に合わないと `read_text()` が直前の内容を返す。

3. **失敗が古い内容の再表示として現れる**
   `structured.unwrap_or(copied)` は HTML フレーバーを優先するため、コピーが失敗すると
   前回コピー時に残っていた HTML が Markdown 化されて表示される。
   ユーザーからは「関係ない古い文章が出る」という形でしか失敗が見えない。

## スコープ

選択テキスト取得の信頼性のみ。「選択なしで起動して手入力する」用途は
既存の `#mo-text`（[index.html](../../index.html) の入力欄）と ✕ ボタンで足りており、
専用の導線は作らない。フロントエンドは空文字ペイロードを
[main.ts](../../src/main.ts) の `hotkey-fired` ハンドラで正しくモードオーバーレイに
フォールバックさせるため、変更不要。

## 方針

固定 sleep による「決め打ちの待ち」を、実測に基づくポーリングに置き換える。
通常ケース（ローカル・選択あり）は現状より速く抜け、RDP 遅延時だけ長く待つ。

### 1. 修飾キーの解放待ち

Ctrl+C を送る前に、Ctrl / Shift / Alt / Win が物理的に離れるまで
`GetAsyncKeyState` を 10ms 間隔で最大 400ms ポーリングする。離れたら即座に次へ進む。
タイムアウトした場合は現状どおり合成 Release を撃ってから続行する（現状より悪化しない）。

`GetAsyncKeyState` は `Win32_UI_Input_KeyboardAndMouse` feature が必要なため、
`src-tauri/Cargo.toml` の `windows-sys` に追加する。

### 2. コピー成立の検出

Ctrl+C 送信前に `GetClipboardSequenceNumber()` を控え、送信後は番号が変化するまで待つ。
`GetClipboardSequenceNumber` は既存の `Win32_System_DataExchange` feature に含まれる。

ただし**番号の変化はコピーの完了ではなく開始の合図**である。番号は `EmptyClipboard()` の
時点で増えるため、変化を合図に読みにいくと書き込み中のクリップボードから空文字を掴む。
実測（Fork、8 回中 3 回）でこれが起きた。したがって判定条件は番号の変化ではなく
**「空でないテキストが実際に読めたこと」**とし、読めるまで 25ms 間隔で最大 1500ms 粘る。
他プロセスがクリップボードをロックしていて読み取り自体が失敗する場合も同じループで吸収される。

待ち時間は環境差が大きい。実測では大半が 30〜40ms で終わる一方、6 回に 1 回ほど
約 1000ms かかった（原因未特定。1 秒ちょうどに寄るため、どこかのタイムアウトが疑わしい）。

### 3. 失敗時の扱い

シーケンス番号が変化しなかった場合は「選択なし、またはコピー失敗」と確定し、
`prev_clipboard` も HTML フレーバーも採用せず空文字を emit する。
空のオーバーレイが開くことで状態が一目でわかる。

`safe_to_copy == false`（ターミナル・エディタ等、Ctrl+C を送ると危険な前景プロセス）の
経路は従来どおり、現在のクリップボード内容をそのまま初期値にする。意図的に
クリップボードを使う経路なので変更しない。

## 構成

`hotkey_handler` は「待つ」「読む」「決める」を混ぜて持っているので、決定ロジックを
純粋関数に切り出す。

| 単位 | 責務 | 依存 |
|------|------|------|
| `wait_for_modifiers_released(timeout)` | 修飾キーが離れるまで待つ。離れたら true | `GetAsyncKeyState` |
| `wait_for_copied_text(before_seq, timeout, on_copy_started)` | 空でないテキストが読めるまで待つ。読めたら `Some` | `GetClipboardSequenceNumber` |
| `decide_text(copied, html_md, changed)` | 表示するテキストを決める純粋関数 | なし |
| `foreground_process_name()` / `foreground_is_self()` | 前景アプリの判定 | `GetForegroundWindow` |
| `hotkey_handler` | 上記を順に呼び、ウィンドウ表示と emit を行う | 上記すべて |

ポーリング関数はロジックを持たない薄いラッパにし、判断は `decide_text` に集約する。

### `decide_text` の仕様

| `changed` | 返り値 |
|-----------|--------|
| `true` | `html_md` があればそれ、なければ `copied` |
| `false` | 空文字 |

`prev_clipboard` はこの関数に渡さない。失敗時のフォールバック先として使わないと決めた以上、
引数に持たせると誤用の余地が残るため。復元処理（コピー成功時に元のクリップボードへ戻す）だけが
`hotkey_handler` 側で `prev_clipboard` を使う。

`safe_to_copy == false` の経路はこの関数を通さず、従来どおり
`clipboard_html_as_markdown().unwrap_or(prev_clipboard)` を使う。

## テスト

Win32 API を叩く 2 つのポーリング関数はユニットテストできない。ロジックを持たせないのは
このため。`decide_text` には [lib.rs](../../src-tauri/src/lib.rs) の既存
`#[cfg(test)] mod html_to_markdown_tests` と同じ形でテストを付ける。

- コピー成功・HTML あり → HTML 由来の Markdown を返す
- コピー成功・HTML なし → 平文を返す
- コピー失敗 → 空文字を返す（`prev` にも `html_md` にも値があっても採用しない）

実機確認は RDP 経由と Alt+T の両方で、選択あり／選択なしの 4 通り。

Win32 側は対話的に観察できない（ホットキー処理は他アプリが前面のまま走る）ため、
`SNAPGLOSS_DEBUG` を設定したときだけ `%TEMP%\snapgloss-hotkey.log` に 1 行残す計測を置く。
上記の「番号の変化 ≠ 読める」も、この計測なしには特定できなかった。使い方は README を参照。

## 取得待ちの可視化

取得完了までの時間が環境により 30ms〜1500ms とばらつくので、待ちを隠さず見せる。

- Ctrl+C を**送った後**、番号の変化（＝コピー開始）を検知した時点でウィンドウを表示し、
  `hotkey-pending` を emit する。送る前に表示するとフォーカスを奪い、前景アプリに
  キーが届かなくなるため、この順序でなければならない
- フロントは取得中であることを入力欄の上に出す。ただし 150ms 以内に終わったときは
  何も出さない（大半のケースで、出すとちらつくだけになる）
- 空欄と区別が付くよう、バーではなくスピナーと文言を置く。「取得に失敗して空欄」と
  「取得中」を見た目で混同させない
- 待っている間にユーザーが入力を始めていたら、遅れて届いたテキストで上書きしない。
  同様に、閉じられていたら開き直さない

前景が SnapGloss 自身のとき（オーバーレイ表示中のホットキー再押下）は取得自体を行わない。
自分に Ctrl+C を送っても番号が動かず、タイムアウトぶん待たされるだけになるため。

## 非目標

- 待ち時間の設定項目化（正しい値を人間に当てさせる設計になるため）
- UI Automation による選択範囲の直接取得（非対応アプリが多く、RDP 越しの内容は原理的に取れない）
- クリップボードを一切汚さない方式への移行

## 追記（2026-09-27）

その後の変更で、上の記述と実装がずれた箇所。本文は当時の判断の記録として残す。

- **待ち時間**：「最大 1500ms 粘る」は 2 段階になった。600ms 待ってクリップボードの
  番号が一度も動いていなければ Ctrl+C を送り直し、さらに 1200ms 待つ。番号が動いて
  いる（コピーは始まっていて読めるだけ遅い）ときは送り直さず待つだけ。送り直しは
  非アクティブ表示のウィンドウに影響されず前景アプリに届く
- **Ctrl+C の送り方**：enigo の `Key::Unicode('c')` は文字として届き、仮想キーを見る
  ペインではコピーにならなかった。Windows では仮想キー＋スキャンコードで SendInput する
- **Alt を含むホットキー**：本キーを OS が飲み込むと前景アプリには「Alt 単独」が届いて
  メニュー待ちに入る。Alt が離される前にマスクキー（VK 0xFF）を 1 回送って防ぐ
- **`safe_to_copy == false` の対象**：「ターミナル・エディタ等」のうちエディタは既定から
  外した（内蔵ターミナルのために本体での取得を潰す実害のほうが大きい）。一覧は設定で
  編集できる
- **ウィンドウの表示タイミング**：「番号の変化を検知した時点で表示」から「Ctrl+C を
  送った直後にフォーカスを奪わずに表示」に変えた。選択なしで押しても即座に反応が見える
